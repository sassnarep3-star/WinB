How this page fits the review surfaces

Three suggestion surfaces exist, and each holds a different kind of decision. The decision board holds the queued proposals with cost, reversibility and failure mode. Design & trends holds the design suggestions, the topic titles and the design prompt. The Decision Room holds the operational priorities. This page holds the register generation’s original ledger: what each suggestion fixes, what evidence would show it worked, and which of three coherent business paths it belongs to. Reply anywhere with an ID and an option letter — for example SG-02: B — and the choice is written into the log at the bottom of this page. Until a row appears there, nothing here has been changed.

Part one

Choose a path, not a feature

These three are business positions — what the site is willing to show and where its evidence comes from. They differ from the three build-order paths on Design & trends, which decide what gets built first; a site picks one of each. The current build is Path A.

Live now

Path A — The honest shop

Publish only what is verifiable. Label every claim. Show no prices until an authorised data route exists. Small, defensible, slow to grow.

Why it wins: it cannot be penalised for false claims, and it is the only path that can be built entirely from documents.

Why it loses: it will not out-convert a site that shows prices and ratings, because buyers want numbers.

Recommended

Path B — Open the data taps

Apply for Product Advertising API access and use SiteStripe. Show price and availability with the required timestamp and disclaimer. Keep every label. Add measurement.

Why it wins: it converts the site's main disadvantage into its main feature — live data with an auditable trail.

Why it loses: depends on an approval the owner does not control yet.

Highest ceiling

Path C — Become a test desk

Buy units, test them, publish protocols and results. Hire nothing; publish the method. This is the only path that justifies the word “reviewed”.

Why it wins: original data is the one thing a competing site cannot copy.

Why it loses: it needs spend and time before the first publishable result.

If you only choose once

Path B, in this order. (1) Confirm the Associates account and the tag — nothing else matters until it is done. (2) Run the one-link test and confirm a click appears in the report. (3) Turn on the event endpoint. (4) Apply for API access. Everything else is optimisation in front of those four; doing them in a different order is how sites end up with beautiful pages and no data.

Standing rules for anything chosen from this page

Every implementation must keep the disclosure strip above the masthead on every page; keep rel="sponsored nofollow noopener" and the tag on every Amazon link; show no price, rating or popularity ranking; state what it could not verify; and pass every build gate (verify, editorial rules, register check, link check, smoke) before it merges. A suggestion that cannot keep those is rejected here, in writing, with its source.

No search-volume, popularity or superiority claim is made anywhere on this page: no keyword tool was consulted, and every row is a proposal, not a measurement. Sources for the rules above: Associates Program Policies · Operating Agreement · FTC Disclosures 101 · Google: qualify outbound links.
